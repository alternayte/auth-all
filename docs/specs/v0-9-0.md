# v0.9.0: key permissions, passkeys, ID token claims, host-issued sessions

## What it does
An organization API key with its own role holds only the intersection of that role and the live permissions of the owner (#26).
A `passkeys` plugin lets a signed-in user register passkeys, list them, delete them, and sign in with them (#27).
An OIDC sign-in hands every verified ID token claim to a new hook, and that hook runs before the TOTP step (#28).
An exported `IssueSession` method creates a session after a sign-in that the host verified itself, for example SAML (#29).

## Decisions
- The release is v0.9.0 — #27, #28 and #29 add exported API.
- `plugin.OrganizationContext` gains `Exact bool`. When it is true, `activePermissions` uses `Permissions` alone and adds neither the membership role nor the team roles — the intersection otherwise widens back to the role of the owner.
- The intersection keeps each statement of either side that the other side covers, so `project:*` and `project:read` give `project:read` — the old one-way intersection gave a wildcard key role over a narrow member nothing, which the owner role used to hide.
- The core sets `Exact` for every principal that has an API key. `KeyCredential` returns the whole live set of the owner for a key with no role, and the intersection for a key with a role — a key with no role keeps the owner's custom role and team roles, as it does today.
- The passkeys plugin uses `github.com/go-webauthn/webauthn` v0.18.2 in the core module. `go.mod` and `humaauth/go.mod` declare `go 1.26.0`, and the README says Go 1.26 — the library is maintained, and v0.18.2 needs Go 1.26.
- A passkey sign-in with the UV flag set issues the session at once. Without UV, a user with confirmed TOTP gets the MFA challenge — with UV, the passkey already gives two factors.
- Registration and delete need a fresh session: a session created less than `FreshAge` ago (default 10 minutes). An older session gets 403 `SESSION_NOT_FRESH` — a stolen cookie must not become a lasting passkey.
- Sign-in is discoverable only, and begin takes no email. Registration sets `residentKey: required` and `userVerification: preferred` — the email form leaks whether an account exists.
- Routes: `POST /passkeys/register/begin`, `POST /passkeys/register/finish`, `POST /passkeys/sign-in/begin`, `POST /passkeys/sign-in/finish`, `GET /passkeys`, `DELETE /passkeys/{id}`. Each route has an OpenAPI operation and a TypeScript client method — the client gets them with no extra work.
- Registration takes a label of 1 to 100 characters. A user holds several passkeys, and a credential ID is unique — the list must name each device.
- Each ceremony writes a challenge row in a table the plugin owns: digest of the ceremony handle, kind, user id (nullable), the go-webauthn session data, expiry 5 minutes, consumed. Finish consumes the row in one statement — go-webauthn requires server-side session data, and a token row has no data column.
- The plugin owns two tables, `passkeys` and `passkey_challenges`, delivered as new migration units. Store access goes through `store.PasskeyStore` in `store/ext.go`, and both adapters and `storetest` implement it — the same pattern as `APIKeyStore`.
- A sign-count clone warning refuses the sign-in and emits `auth.passkey_clone_detected`. A counter that stays 0 is no warning — a synced passkey always reports 0.
- Each sign-in writes back the sign count, the UV flag, the backup state and the last use time.
- `plugin.SignInService` (optional, in `services_ext.go`) gives a plugin the disabled check, the verified-address check, and the AuthResponse body of the core routes — a plugin cannot build the user body, because it does not know the host user fields.
- A disabled user and an unverified email under `RequireEmailVerification` are refused as `SignIn` refuses them. The session method is `passkey` — every sign-in path keeps the same rules.
- The sign-in routes count against a new rate limit operation `passkey-sign-in` keyed by IP — the same guard as the password route.
- Options: `RPID`, `RPDisplayName`, `Origins` (default: the origin of the base URL), `UserVerification`, `FreshAge`. Construction fails when the base URL is a runtime source and `RPID` or `Origins` is missing, and when the RP ID is an IP address — the RP ID binds every stored passkey, and WebAuthn refuses an IP address.
- `plugins/passkeys/passkeystest` exports a virtual authenticator (ES256, `none` attestation, UV flag, sign counter) that builds on the cbor module go-webauthn already requires — a host such as Fettle drives both ceremonies in its own Go tests, and no further dependency is added.
- `oauth.Identity` gains `Claims *oauth.Claims`, a read-only set of every claim of the verified ID token with `Get`, `Strings` and `Map` — a map field would make `Identity` non-comparable, which `just apidiff` refuses. `oauth/oidc` fills it, and so does Google, which builds on it. A provider that verifies no ID token leaves it nil — a fixed list of claim names would need a configuration step for each IdP.
- `hook.Hooks` gains `OnBeforeOAuthSignIn(ev *hook.OAuthSignIn{User, Provider, Identity, Tx})`. The callback runs it in a transaction after the user resolves and before the TOTP check, the link callback included, because it signs the user in too. An error refuses the sign-in — it fires for TOTP users too, and a host can refuse a sign-in by group.
- `OnBeforeUserCreate` gets the claims through the `Identity` it already carries.
- `Auth.IssueSession(ctx, IssueSessionInput{UserID, Method, PreviousSessionToken, SkipMFA}) (*SignInResult, error)` refuses a disabled user, runs the MFA check unless `SkipMFA` is true, creates the session, and runs the sign-in hooks and the audit event. It writes no cookie, and the host calls `SetSessionCookie` — the same contract as `SignIn`.
- `IssueSession` refuses an empty `Method`, and it applies no rate limit — the host verified the credential, and the rate limit guards password guessing.

## Out
- Passkey sign-up without an account, a passkey rename, and email-scoped sign-in.
- Attestation verification other than `none`, and the FIDO metadata service.
- Storage of ID token claims. A SAML implementation inside Auth-All.
- `Claims` on `hook.SignIn`.

## How I know it works
- An editor creates a `reader` key in an organization. `Can(ctx, "sandbox:write")` with that key returns false, and `Can(ctx, "sandbox:read")` returns true.
- A key with no role, owned by a member with a custom role, passes `Can` for each statement of that custom role.
- `go run ./examples/go-app` serves the passkey routes. In a browser, a signed-in user registers a passkey and signs out. That user then signs in with the passkey and gets no TOTP prompt.
- A Go test drives registration and sign-in through `passkeystest` against both stores. A replayed finish gets 400, and a session older than 10 minutes gets 403 `SESSION_NOT_FRESH`.
- An OIDC sign-in from a fake IdP with `"groups": ["acme-owners"]` shows the groups in `OnBeforeOAuthSignIn`, and the hook runs for a user with TOTP too. A hook error refuses the sign-in.
- `IssueSession` for a user with TOTP returns `MFARequired: true` and no session. With `SkipMFA` it returns a session, and the audit event names the method.
- `just generate` changes `api/openapi.json` and the TypeScript client. `just verify` passes. `just apidiff` reports additions only.
